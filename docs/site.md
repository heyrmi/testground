# About this site

This documentation is static HTML, generated by a small Go program that lives
in the repository at `docs/gen`. It has no runtime dependencies: no script, no
web fonts, no icon set, no analytics, and no request to any host. Opened from a
`file://` path it behaves exactly as it does when served, which is the same
promise the playground itself makes.

## Why not MkDocs or Docusaurus

The honest comparison is with MkDocs and the Material theme, which would have
been less work. It renders Markdown properly rather than the subset described
below, it has search, and its assets can be vendored so that nothing is fetched
at view time.

What it costs is a third toolchain. This project's stated requirement is Go and
Node and nothing else, its Go dependencies are capped at ten because people
audit it before running it inside a corporate network, and every frontend asset
is vendored rather than linked. Adding Python and a theme's asset tree to build
the page that explains those choices is a strange trade. Docusaurus is worse
for the same reasons and one more: it would ship a React runtime to read a
paragraph.

Against that, a generator has to be written and maintained. It came to a few
hundred lines of standard library because the requirement is narrow — eight
pages, one stylesheet, and a catalogue read from JSON — and because it renders
a deliberately small subset of Markdown rather than the whole language. If this
site ever needs search, versioned documentation or translation, that judgement
should be revisited rather than defended; the source Markdown would move to
another generator unchanged.

## Building it

```sh
go run ./docs/gen                       # writes docs/_site
open docs/_site/index.html              # no server required
```

To read it over HTTP instead, which is worth doing before publishing:

```sh
go run ./docs/gen -serve 127.0.0.1:7575
```

The generator obtains the catalogue by running `go run ./cmd/playground
manifest` for itself. Where a binary already exists — in CI, or after a
`make` — hand it the JSON instead and save the second compile:

```sh
./playground manifest > manifest.json
go run ./docs/gen -manifest manifest.json
```

The output directory is rebuilt from empty on every run, and `docs/_site` is
ignored by git. Nothing generated is committed.

## Adding a page

1. Write the Markdown under `docs/`. The first level-one heading becomes the
   page title; a file without one fails the build rather than publishing a
   page with the wrong name in the browser tab.
2. Add one line to the `pages` table in `docs/gen/main.go`, giving its slug,
   its source path, its label in the sidebar and the line that appears under
   that label. The table is the running order, and a page nobody lists is not
   published — which is deliberate, since an unreachable page is worse than an
   absent one.

A page's source may be any Markdown file in the repository, not only one under
`docs/`. The contributing page is `CONTRIBUTING.md` at the root, rendered
rather than copied, because the copy is what goes stale.

## The Markdown subset

Supported: headings, paragraphs, bullet and numbered lists including nesting,
fenced code blocks, tables with alignment, blockquotes, thematic breaks, and
four inline forms — `` `code` ``, `**strong**`, `*emphasis*` and
`[links](site.md)`.

Two omissions are deliberate rather than pending:

- **Underscores are not emphasis.** This documentation is full of field and
  file names that contain them, and a rule that turns half an identifier
  italic is worse than having no italics.
- **Raw HTML is not passed through.** It is escaped and shown. A page that
  needs markup the subset cannot express should say so in review, not smuggle
  it in.

Anything else unrecognised falls through to an escaped paragraph, so a document
that strays outside the subset reads as obviously wrong rather than quietly
losing a sentence.

## Links are checked

A link that names a page of this site becomes a relative link between the
built files, which is what lets the site be read from a file path and from a
Pages subdirectory without either needing to know its own base URL.

Any other target must at least exist in the repository, and is rewritten to
point at it on GitHub. A target that is neither — a renamed page, a mistyped
path — fails the build. Documentation whose internal links quietly rot is the
thing this whole project is a reaction to, so it is not allowed to happen
here.

## Generated sections

A line consisting of an HTML comment in this form is replaced with generated
content:

```
<!--generated:catalogue-->
```

The comment form matters: a source file still reads correctly on GitHub, where
the generated section is simply absent rather than showing a broken directive.
Four names exist, all reading the challenge manifest:

| Name | What it inserts |
|---|---|
| `catalogue-stats` | Counts of challenges, zones, concepts, tags and selectors, and the tier spread |
| `challenge-index` | A table of every challenge, linking into the detail below it |
| `catalogue` | The full detail for every challenge, grouped by zone |
| `zone-table` | The zones, their prefixes, technologies and challenge counts |

An unknown name fails the build. A hole that silently rendered nothing would
leave a page that is merely shorter than it should be, which is exactly the
kind of omission that survives review.

## How it is published

`.github/workflows/docs.yml` builds the site and deploys it to GitHub Pages on
every push to `main` that touches the documentation, the challenge
declarations or the workflow itself. Pull requests build it too, without
deploying, so a broken link or a page that no longer renders is caught before
it merges rather than after.

The catalogue is rebuilt from the challenge registry on every deploy, so it
cannot be stale relative to `main`. It can be ahead of the latest release: what
is published here is what `main` serves, and a challenge added since the last
tag appears on this site before it appears in a version anyone can install.
